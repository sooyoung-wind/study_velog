study_hello — React + Apollo + GraphQL 학습 가이드

4가지 기술이 각각 뭔지

식당에 비유해서 설명합니다.

GraphQL = 메뉴판 + 주문서 양식

클라이언트(손님)와 서버(주방) 사이의 대화 규칙이다.

  • 서버가 "나는 이런 데이터를 줄 수 있어"라고 메뉴판(스키마)을 정의
  • 클라이언트가 "이 데이터 주세요"라고 주문서(쿼리)를 보냄
Apollo Server = 주방

메뉴판을 가지고 실제로 요리를 만들어주는 곳. 손님이 hello를 주문하면 "Hello from Apollo Server 5!"를 돌려준다.

React = 인테리어 + 테이블 배치

손님(사용자)이 보는 화면을 만드는 도구. HTML을 직접 쓰는 대신 컴포넌트라는 레고 블록으로 조립한다.

Apollo Client = 웨이터

React 화면과 Apollo Server 사이를 오가며 주문을 전달하고 결과를 가져다주는 역할.

전체 동작 흐름

사용자가 브라우저에서 http://localhost:5173을 열면 이런 일이 벌어집니다.

index.html 로드
빈 HTML 껍데기. <div id="root">라는 빈 공간만 있다.
main.jsx 실행
Apollo Client(웨이터) 생성 + React 앱 시작.
App.jsx — 주문
"hello 데이터 주세요" → POST http://localhost:4000/ 요청 전송.
server/index.js — 응답
요청을 받아 resolver 실행 → "Hello from Apollo Server 5!" 반환.
App.jsx — 화면 표시
받은 데이터를 화면에 렌더링. "GraphQL response: Hello from Apollo Server 5!"
핵심: 서버(포트 4000)와 클라이언트(포트 5173)는 별도 프로세스로 실행된다. 서버는 데이터를 제공하고, 클라이언트는 화면을 보여준다.

서버 코드 해설 — server/src/index.js

import { ApolloServer } from '@apollo/server';
import { startStandaloneServer } from '@apollo/server/standalone';

// ① 메뉴판 (스키마): "hello를 물어보면 String을 줄 수 있어"
const typeDefs = `#graphql
  type Query {
    hello: String
  }
`;

// ② 요리법 (리졸버): 실제로 데이터를 만드는 함수
const resolvers = {
  Query: {
    hello: () => 'Hello from Apollo Server 5!',
  },
};

// ③ 서버 생성 + 포트 4000에서 실행
const server = new ApolloServer({ typeDefs, resolvers });
const { url } = await startStandaloneServer(server, {
  listen: { port: 4000 },
});
console.log(`Server ready at ${url}`);
코드역할비유
typeDefs요청 가능한 데이터의 타입 정의메뉴판
resolvers실제 데이터를 반환하는 함수요리법
ApolloServer서버 인스턴스 생성주방 오픈
startStandaloneServerHTTP 서버 시작영업 시작

App.jsx — 실제 화면

import { useQuery, gql } from '@apollo/client';

// 주문서: "hello 데이터를 주세요"
const HELLO_QUERY = gql`
  query HelloQuery {
    hello
  }
`;

function App() {
  // useQuery가 서버에 자동으로 요청을 보낸다
  const { loading, error, data } = useQuery(HELLO_QUERY);
  //       ↑ 로딩중?   ↑ 에러?   ↑ 받은 데이터  (Apollo가 자동으로 관리)

  if (loading) return <p>Loading...</p>;
  if (error)   return <p>Error: {error.message}</p>;

  return <p>GraphQL response: <strong>{data.hello}</strong></p>;
}

서버에 어떤 요청이 가능한지 어떻게 알 수 있나?

방법 1: 코드를 직접 보는 법

서버의 typeDefs(스키마 = 메뉴판)를 보면 된다.

const typeDefs = `#graphql
  type Query {
    hello: String   // "hello"만 요청 가능
  }
`;

지금은 hello: String 하나뿐이니까, 클라이언트가 요청할 수 있는 건 hello 딱 하나뿐이다.

방법 2: GraphQL Sandbox (실행 중일 때)

서버를 실행한 뒤 브라우저에서 http://localhost:4000을 열면 Apollo Sandbox가 나온다. 이건 GraphQL이 기본 제공하는 "메뉴판 조회 기능(Introspection)"을 이용한 것이다.

  • 왼쪽에 사용 가능한 쿼리 목록이 자동으로 표시됨
  • 직접 쿼리를 타이핑해서 즉시 테스트 가능

다른 요청을 추가하고 싶다면

스키마와 리졸버에 추가하면 된다. goodbye를 추가하는 예시:

const typeDefs = `#graphql
  type Query {
    hello: String
    goodbye: String   // 추가
  }
`;

const resolvers = {
  Query: {
    hello: () => 'Hello from Apollo Server 5!',
    goodbye: () => 'Goodbye! See you later!',   // 추가
  },
};

그러면 클라이언트에서 이렇게 요청할 수 있다:

{ hello }          # hello만 요청
{ goodbye }        # goodbye만 요청
{ hello, goodbye } # 둘 다 한번에 요청 ← 이게 GraphQL의 장점!
GraphQL의 큰 장점: 서버가 "나는 이런 데이터를 줄 수 있어"라고 스키마로 명확히 선언하기 때문에, 클라이언트 개발자가 문서 없이도 무엇을 요청할 수 있는지 바로 알 수 있다.

redux-pender가 하는 일

axios 요청(비동기 작업)을 자동으로 3단계로 나눠준다.

버튼 클릭 │ ▼ dispatch(fetchHelloAction()) ← payload = Promise │ ▼ redux-pender 미들웨어가 Promise를 감지 │ ├─[요청 시작]──► FETCH_HELLO_PENDING → loading: true │ ├─[성공]────────► FETCH_HELLO_SUCCESS → loading: false, message: "Hello from Koa!" │ └─[실패]────────► FETCH_HELLO_FAILURE → loading: false, error: ...
상황추천 방식
단순한 데이터 조회Apollo useQuery
상태 변화가 복잡하고 여러 컴포넌트가 공유Redux
단순한 CRUD 작업REST API
여러 종류의 데이터를 한 번에 요청GraphQL

① server/src/index.js — Koa 서버

import Koa from 'koa';           // Python의 Flask/FastAPI 같은 것
import Router from 'koa-router'; // URL 경로를 등록하는 도구
import bodyParser from 'koa-bodyparser'; // POST 요청 본문을 읽어주는 도구
import cors from '@koa/cors';    // 다른 포트 요청을 허용

const app = new Koa();    // 서버 인스턴스 (FastAPI의 app = FastAPI()와 같다)
const router = new Router(); // URL 경로 묶음

app.use(cors());          // 모든 요청에서 CORS 허용
app.use(bodyParser());    // 모든 요청에서 본문 파싱

router.get('/api/hello', (ctx) => {
  ctx.body = { message: 'Hello from Koa!' }; // ctx.body = 응답 데이터
});

app.use(router.routes());       // router에 등록한 경로를 app에 붙임
app.use(router.allowedMethods()); // 허용 안 된 메서드엔 405 자동 반환

app.listen(4001, () => {
  console.log('Koa server running on http://localhost:4001');
});
CORS가 필요한 이유: 브라우저는 기본적으로 다른 포트로 요청을 막는다. 클라이언트(5173)가 서버(4001)로 요청할 때 포트가 다르므로, 서버에서 cors()로 허용해야 한다.

③ store/modules/hello.js — Redux 상태 관리 로직

Redux란?

앱 전체의 데이터를 한 곳에서 관리하는 도구다.

Redux가 없으면: 컴포넌트A → 컴포넌트B → 컴포넌트C 로 데이터를 일일이 전달해야 함 Redux가 있으면: 모든 컴포넌트 → 중앙 저장소(store)에서 직접 데이터를 꺼냄
import { createAction, handleActions } from 'redux-actions';
import { pender } from 'redux-pender';
import { fetchHello } from '../../api/helloApi';

// Action 타입 (문자열 상수)
const FETCH_HELLO = 'hello/FETCH_HELLO';

// Action creator: 실행하면 { type: FETCH_HELLO, payload: Promise } 생성
export const fetchHelloAction = createAction(FETCH_HELLO, () => fetchHello());

// 초기 상태
const initialState = {
  message: null,   // 서버에서 받은 메시지 (처음엔 없음)
  loading: false,  // 요청 중인가? (처음엔 아님)
  error: null,     // 에러가 있는가? (처음엔 없음)
};

// Reducer: "어떤 액션이 오면 상태를 어떻게 바꿀지" 정의
export default handleActions(
  {
    ...pender({          // pender가 PENDING / SUCCESS / FAILURE 세 가지를 자동 생성
      type: FETCH_HELLO,
      onPending: (state) => ({
        ...state,        // 기존 상태 복사 (Python의 {**state}와 같다)
        loading: true,
        error: null,
      }),
      onSuccess: (state, action) => ({
        ...state,
        loading: false,
        message: action.payload.data.message, // axios 응답 구조: payload.data.message
      }),
      onFailure: (state, action) => ({
        ...state,
        loading: false,
        error: action.payload,
      }),
    }),
  },
  initialState
);
...state가 뭔가? 스프레드 연산자. "기존 상태를 그대로 복사하고, 그 다음에 오는 것만 바꿔라"는 뜻. Python의 {**state, "loading": True}와 같다.

axios 응답 구조

// action.payload.data.message를 쓰는 이유:
// axios가 응답을 이렇게 감싸기 때문이다
action = {
  payload: {              // axios 응답 객체
    data: {               // 서버가 실제로 보낸 JSON
      message: "Hello from Koa!"   // 우리가 원하는 값
    },
    status: 200,
    // ...
  }
}

④ store/index.js — Redux 저장소 만들기

import { createStore, combineReducers, applyMiddleware } from 'redux';
import penderMiddleware from 'redux-pender';
import hello from './modules/hello';

// 여러 모듈의 reducer를 하나로 합침
// 결과: { hello: { message, loading, error } }
const rootReducer = combineReducers({ hello });

// 저장소 생성 + 미들웨어 등록
const store = createStore(rootReducer, applyMiddleware(penderMiddleware()));
//                                      ↑ dispatch → reducer 사이에서 Promise를 감지

export default store;
미들웨어란? 액션이 dispatch되고 reducer에 도달하기 전에 중간에서 처리하는 것. penderMiddleware가 없으면 Redux는 Promise를 그냥 저장해버린다. 미들웨어가 있어야 비동기 요청의 3단계(PENDING/SUCCESS/FAILURE)로 나눠준다.

⑥ App.jsx — 화면에 보이는 컴포넌트

import { useDispatch, useSelector } from 'react-redux';
import { fetchHelloAction } from './store/modules/hello';

function App() {
  const dispatch = useDispatch();
  // store에서 hello 상태를 꺼낸다
  // state.hello인 이유: combineReducers({ hello })로 만들었기 때문
  const { message, loading, error } = useSelector((state) => state.hello);

  const handleClick = () => {
    dispatch(fetchHelloAction()); // 버튼 클릭 → 액션 dispatch
  };

  return (
    <div>
      <h1>Study Hello Koa</h1>

      {/* disabled={loading}: 요청 중엔 버튼 비활성화 (중복 요청 방지) */}
      <button onClick={handleClick} disabled={loading}>
        {loading ? 'Loading...' : 'Fetch Hello'}
      </button>

      {/* message가 있을 때만 보여준다 (Python의 if message: 와 같다) */}
      {message && <p>Response: <strong>{message}</strong></p>}
      {error   && <p style={{ color: 'red' }}>Error: {String(error)}</p>}
    </div>
  );
}

Python 유저 입장에서 REST vs GraphQL 선택 가이드

결론부터: REST API가 보편적으로 합리적인 선택이다. 단, "항상 REST"는 아니다.

왜 Python 유저에게 REST가 더 자연스러운가

① 생태계가 REST 중심으로 성숙해 있다

프레임워크REST 지원GraphQL 지원

DjangoDRF로 성숙graphene-django로 추가 가능

        return "Hello!"

② ML / 데이터 과학 생태계와 자연스럽게 연결된다

pandas / sklearn / pytorch로 모델 학습 │ ▼ FastAPI로 모델을 REST API로 감쌈 │ ▼ POST /predict → { "result": 0.87 } │ ▼ 프론트엔드 / 앱 / 다른 서비스가 호출

Hugging Face, OpenAI, Anthropic 등 대부분의 AI API가 REST 방식이다.

③ 디버깅과 테스트가 훨씬 쉽다

REST — curl 한 줄
curl http://localhost:8000/api/users/1
GraphQL — JSON 본문 필요
curl -X POST http://localhost:8000/graphql \
  -H "Content-Type: application/json" \
  -d '{"query": "{ user(id: 1) { name email } }"}'

그렇다면 GraphQL은 언제 선택하는가

상황선택
FastAPI / Django로 백엔드 처음 만든다REST
ML 모델을 API로 배포한다REST
외부 서비스 / 앱이 내 API를 쓴다REST
모바일 + 웹이 같은 서버를 쓰고 데이터 형태가 다르다GraphQL 검토
프론트엔드 팀이 Apollo를 쓴다GraphQL
연관 데이터를 한 번에 요청해야 하는 경우가 많다GraphQL 검토
Python으로 서버를 처음 만든다면 REST(FastAPI)로 시작하고, 프론트엔드의 데이터 요구가 복잡해지는 시점에 GraphQL을 검토하면 된다. GraphQL은 "더 좋은" 방식이 아니라 특정 문제를 해결하기 위한 방식이다.
6

"프론트엔드 데이터 요구가 복잡하다"는 게 무슨 뜻인가?

대용량 데이터와는 관계없다. 같은 데이터를 화면마다 다른 형태로 요청한다는 뜻이다.

구체적인 예시: 인스타그램 같은 SNS

"게시글(Post)" 데이터가 서버에 이렇게 저장되어 있다고 하자.

Post {
  id
  image_url
  content         (본문, 최대 2000자)
  created_at
  like_count
  author {
    id, username, profile_image
    bio             (자기소개, 최대 500자)
    follower_count
  }
  comments [
    { id, content, author { username } }
    ... 수백 개
  ]
  tags [ "여행", "맛집", ... ]
}

이 데이터가 필요한 화면이 3개 있다

화면필요한 필드불필요한 것
피드 목록 (스크롤 화면) image_url, like_count, author.username, 본문 30자 댓글 전체, 본문 나머지, bio…
게시글 상세 전부 + comments 전체 + tags 없음
알림 목록 image_url, author.username 딱 2개 나머지 전부

REST라면 어떤 문제가 생기나

방법 A: 화면마다 엔드포인트를 만든다

GET /posts/feed               → 피드용 데이터
GET /posts/{id}               → 상세용 데이터
GET /posts/notification-preview → 알림용 데이터

화면이 10개면 엔드포인트가 10개. 화면 디자인이 바뀔 때마다 백엔드도 수정해야 한다.

문제: 프론트: "피드에 댓글 수도 보여주고 싶어요" → 백엔드 수정 → 프론트: "역시 필요 없을 것 같아요" → 백엔드 또 수정…

방법 B: 항상 전체 데이터를 준다

알림 화면은 2개 필드만 필요한데, 댓글 수백 개를 받아서 99%를 버린다.

Over-fetching 문제: 알림이 1000개면 → 불필요한 댓글 데이터를 347,000개 받아서 버리는 셈이다.

GraphQL이라면

엔드포인트는 하나(/graphql). 클라이언트가 필요한 필드만 골라서 요청한다.

피드에서 요청
query {
  posts {
    image_url
    like_count
    author { username }
    content
  }
}
알림에서 요청
query {
  post(id: 1) {
    image_url
    author { username }
  }
  # 댓글 347개 → 아예 요청 안 함

정리

오해실제 의미
데이터 양이 많다 (대용량)❌ 아니다
화면마다 같은 데이터를 다른 형태로 필요로 한다✅ 이게 맞다
혼자 만드는 토이 프로젝트라면? 이 문제가 잘 안 생긴다. 화면이 몇 개 없고 프론트·백엔드를 같은 사람이 만드니까 그냥 맞춰주면 된다. GraphQL이 빛나는 건 프론트 팀 / 백엔드 팀이 분리된 큰 서비스에서다.
