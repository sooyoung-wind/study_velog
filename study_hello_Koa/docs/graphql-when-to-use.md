# "프론트엔드 데이터 요구가 복잡하다"는 게 무슨 뜻인가

> 대용량 데이터와는 관계없다. **같은 데이터를 화면마다 다른 형태로 요청한다**는 뜻이다.

---

## 구체적인 예시: 인스타그램 같은 SNS

"게시글(Post)" 데이터가 서버에 이렇게 저장되어 있다고 하자.

```
Post {
  id
  image_url
  content         (본문, 최대 2000자)
  created_at
  like_count
  author {
    id
    username
    profile_image
    bio             (자기소개, 최대 500자)
    follower_count
  }
  comments [
    { id, content, author { username } }
    ...수백 개
  ]
  tags [ "여행", "맛집", ... ]
}
```

### 이 데이터가 필요한 화면이 3개 있다

---

**화면 1: 피드 목록 (스크롤하며 보는 화면)**

```
┌─────────────────┐
│  [이미지]        │
│  ❤️ 좋아요 342   │
│  @username      │
│  여행 맛집...    │  ← 본문 앞 30자만
└─────────────────┘
```

필요한 필드: `image_url`, `like_count`, `author.username`, `content` 앞부분만

---

**화면 2: 게시글 상세 페이지**

```
┌─────────────────┐
│  [이미지]        │
│  @username      │
│  본문 전체...    │
│                 │
│  댓글 347개     │
│  ㄴ @kim: 좋아요 │
│  ㄴ @lee: 멋져요 │
└─────────────────┘
```

필요한 필드: 위의 전부 + `comments` 전체 + `tags`

---

**화면 3: 알림 목록**

```
@username 님이 회원님 게시글에 좋아요를 눌렀습니다.  [이미지 썸네일]
```

필요한 필드: `image_url`, `author.username` 딱 2개만

---

## REST라면 어떤 문제가 생기나

### 방법 A: 엔드포인트를 화면마다 따로 만든다

```
GET /posts/feed      → 피드용 데이터
GET /posts/{id}      → 상세용 데이터
GET /posts/notification-preview  → 알림용 데이터
```

화면이 10개면 엔드포인트가 10개. 화면 디자인이 바뀔 때마다 백엔드도 수정해야 한다.

```
프론트: "피드에 댓글 수도 보여주고 싶어요"
백엔드: "알겠어요, /posts/feed 응답에 comment_count 추가할게요" (백엔드 수정)
프론트: "역시 필요 없을 것 같아요"
백엔드: "...다시 빼드릴게요" (또 수정)
```

---

### 방법 B: 엔드포인트 하나에서 전체 데이터를 항상 다 준다

```
GET /posts/{id}  →  항상 전체 데이터 반환
```

알림 화면은 `image_url`과 `author.username` 2개만 필요한데,
댓글 수백 개, 본문 2000자, 태그 목록 전부를 받아서 99%를 버린다.

```
알림 화면이 받는 데이터 (실제 필요: 2개 필드):

{
  "id": 1,
  "image_url": "...",        ← 필요
  "content": "오늘 방문한 식당은...(2000자)",  ← 버림
  "created_at": "...",       ← 버림
  "like_count": 342,         ← 버림
  "author": {
    "username": "kim",       ← 필요
    "bio": "안녕하세요...(500자)",  ← 버림
    "follower_count": 1200,  ← 버림
    ...
  },
  "comments": [ ...347개... ],  ← 전부 버림
  "tags": [ ... ]            ← 버림
}
```

이게 알림이 1000개면 → 불필요한 댓글 데이터를 347,000개 받아서 버리는 셈이다.
이게 "over-fetching(과다 수신)" 문제다.

---

## GraphQL이라면

엔드포인트는 하나(`/graphql`). 클라이언트가 필요한 필드만 골라서 요청한다.

**피드 목록에서 요청:**
```graphql
query {
  posts {
    image_url
    like_count
    author { username }
    content   # 앞부분 자르는 건 프론트에서 처리
  }
}
```

**알림에서 요청:**
```graphql
query {
  post(id: 1) {
    image_url
    author { username }
  }
}
```

댓글 347개는 아예 요청조차 하지 않으니 서버도 DB에서 안 읽어도 된다.

## 정리

"프론트엔드 데이터 요구가 복잡하다"는 건:

| 오해 | 실제 의미 |
|------|----------|
| 데이터 양이 많다 (대용량) | ❌ |
| **화면마다 같은 데이터를 다른 형태로 필요로 한다** | ✅ |

구체적으로는:
- 화면 A는 필드 3개, 화면 B는 필드 20개, 화면 C는 필드 2개가 필요할 때
- 화면 디자인이 자주 바뀌어서 필요한 필드가 계속 달라질 때
- 모바일 앱(데이터 절약 중요)과 웹(풍부한 데이터)이 같은 서버를 쓸 때

---

## 그럼 Python 백엔드를 혼자 만드는 경우엔?

혼자 만드는 토이 프로젝트나 간단한 서비스라면 이런 상황이 잘 안 생긴다.
화면이 몇 개 없고, 프론트엔드와 백엔드를 같은 사람이 만드니까 그냥 맞춰주면 된다.

GraphQL의 장점이 빛나는 건 **프론트엔드 팀과 백엔드 팀이 분리되어 있고,
화면 종류가 많은 서비스**(앱, 웹, 파트너 API 등)를 만들 때다.
